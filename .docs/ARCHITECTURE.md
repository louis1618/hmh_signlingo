# 시스템 아키텍처 (System Architecture)

본 문서는 **SignLingo**의 전체 시스템 논리 구성, 데이터 흐름, 프로토콜 명세 및 치명적인 도메인 갭(Domain Gap)을 해결하기 위한 기술적 설계를 다룹니다.

---

## 1. 전체 아키텍처 다이어그램 (Overall Architecture)

SignLingo는 온디바이스 비전 처리(MediaPipe), 브라우저 내 3D 렌더링(R3F/VRM), 딥러닝 기반 AI 백엔드(FastAPI/PyTorch), 생성형 AI 파이프라인(Gemini)이 상호작용하는 분산형 실시간 구조를 가지고 있습니다.

```
+---------------------------------------------------------------------------------+
|                                 Client Browser                                  |
|                                                                                 |
|   +--------------------------------+     +----------------------------------+   |
|   |         Webcam Input           |     |          3D Tutor View           |   |
|   +---------------+----------------+     +----------------+-----------------+   |
|                   |                                       ^                     |
|                   v (Raw Video Frames)                    | (Pseudo-MediaPipe)  |
|   +---------------+----------------+                      |                     |
|   |     MediaPipe Vision Tasks     |                      |                     |
|   |   (Pose & Hand Landmarkers)    |                      |                     |
|   +---------------+----------------+                      |                     |
|                   |                                       |                     |
|                   v (3D/2D Landmarks)                     |                     |
|   +---------------+----------------+                      |                     |
|   |  Feature Normalizer (100-dim)  |                      |                     |
|   +---------------+----------------+                      |                     |
|                   |                                       |                     |
|                   v (Normalised Coord)                    |                     |
|   +---------------+----------------+                      |                     |
|   |    Sliding Window (124 Frms)   |                      |                     |
|   +---------------+----------------+                      |                     |
|                   |                                       |                     |
|                   v (Downsampled 60 Frms)                 |                     |
|   +---------------+----------------+                      |                     |
|   |    WebSocket client (Binary)   |                      |                     |
|   +---------------+----------------+                      |                     |
+-------------------|---------------------------------------|---------------------+
                    |                                       |
                    | (24,000 Bytes Float32 array)          | GET /api/motion/{word}
                    v                                       v
+-------------------|---------------------------------------|---------------------+
|                   |             FastAPI Server            |                     |
|                   v                                       |                     |
|   +---------------+----------------+                      |                     |
|   |       WebSocket Handler        |                      |                     |
|   +---------------+----------------+                      |                     |
|                   |                                       |                     |
|                   v (PyTorch Input Buffer)                |                     |
|   +---------------+----------------+                      |                     |
|   |  SignLanguageModel Inference   |                      |                     |
|   |  (Bi-LSTM + Multihead Attn)    |                      |                     |
|   +---------------+----------------+                      |                     |
|                   |                                       |                     |
|                   v (Classification Output)               |                     |
|   +---------------+----------------+     +----------------+-----------------+   |
|   |   Word + Conf (JSON Response)  |     |   np.memmap (dataset_features)   |   |
|   +--------------------------------+     +----------------------------------+   |
+---------------------------------------------------------------------------------+
```

## 2. 데이터 흐름 (Data Flow Paths)

### A. 학습 피드백 루프 (Practice Mode Data Flow)
1. **프레임 캡처:** 사용자의 웹캠 영상을 640x480 해상도로 프론트엔드에서 수신합니다.
2. **골격 추적:** MediaPipe Web SDK가 GPU 런타임에 직접 액세스하여 포즈(33개) 및 양손(각 21개) 랜드마크의 XYZ 좌표를 비디오 프레임 단위로 실시간 추출합니다.
3. **특징 추출 & 정규화:** `mediapipeEngine.js`에서 랜드마크를 추출하여, 훈련 데이터와 동일한 위상 구조(8 포즈 + 42 핸드 = 50 랜드마크)로 재배치하고, `Neck` 기준으로 중심을 잡은 뒤 어깨폭 기준의 `torsoSize`로 나누어 정규화된 100차원 특징(Feature) 벡터를 만듭니다.
4. **버퍼링 및 스케일링:** 100차원 특징 벡터를 순차적으로 슬라이딩 윈도우 버퍼(`slidingWindowRef.current`)에 채워 124프레임(약 4.1초)의 시퀀스를 만들고, 이를 리니어 선형보간을 통해 60프레임으로 압축합니다.
5. **서버 전송:** 압축된 `60프레임 x 100피처 = 6,000개 float32 데이터`를 바이너리 버퍼(24,000바이트)로 변환해 WebSocket으로 백엔드에 즉시 쏩니다.
6. **추론 및 응답:** 백엔드는 커넥션당 할당된 GPU/CPU 텐서 버퍼에 바이너리를 즉시 기록(`torch.frombuffer`)하고 딥러닝 추론을 돌려 예측 단어 및 확신도(Confidence)를 WebSocket으로 반환합니다.
7. **피드백 표출:** 프론트엔드는 수신된 단어가 학습 중인 타겟 단어와 일치하고 임계값(`MIN_CONFIDENCE=0.20`) 이상인 상태가 `CONFIRM_COUNT=3`회 연속 유지되면 미션 성공 처리를 수행합니다.

### B. 아바타 3D 시연 루프 (Tutor Playback Data Flow)
1. 학습방에 입장하면 프론트엔드는 백엔드의 `GET /api/motion/{word}` API를 호출합니다.
2. 백엔드는 대용량 이진 특징 데이터인 `dataset_features.bin` (5.08 GB)을 `np.memmap` 형태로 열어두고 해당 단어의 파일 포인터 오프셋으로 접근합니다.
3. 메모리 폭증 없이 필요한 단어의 60프레임 분량 특징 데이터만 읽어들여 역정규화 및 MediaPipe 규격의 랜드마크 JSON 배열로 재구성하여 프론트엔드에 즉시 반환합니다.
4. 프론트엔드 `AvatarCanvas`는 R3F `useFrame` 렌더 루프 내부에서 프레임 포인터를 100ms마다 이동시키며 `vrmSolver.js`를 호출합니다.
5. `vrmSolver.js`는 `Kalidokit`을 사용하여 랜드마크 데이터로부터 어깨, 팔꿈치, 손목, 손가락 21개 관절의 회전값(Quaternion/Euler)을 계산한 뒤 VRM 아바타의 본 구조에 덮어씌웁니다.

## 3. 핵심 아키텍처 특징 및 엔지니어링 결정

### A. 도메인 갭(Domain Gap) 극복
학습용 AI Hub 데이터는 2D OpenPose로 라벨링되어 있으며, 웹 환경에서 추론할 때는 온디바이스에서 구동하기 쉬운 MediaPipe를 사용합니다. 두 데이터 포맷 간의 수학적 불일치를 해결하기 위해 **프론트엔드 수준의 정밀 위상 매핑 및 중심축/크기 정규화 알고리즘**을 도입했습니다.
* **위상 동기화:** MediaPipe에는 존재하지 않는 `Neck` 좌표를 양 어깨의 가상 중간 좌표로 합성하여 OpenPose와 본(Bone) 정렬을 맞췄습니다.
* **손 붕괴(Hand Collapse) 로직:** 실시간 웹캠 구동 시 손이 뭉개지거나 영역을 벗어나 MediaPipe Hand 랜드마크가 잡히지 않으면, 억지로 손모양 값을 유추하는 대신 전체 손가락 관절 좌표를 손목 좌표 단일 지점으로 붕괴시켜 훈련 데이터와 입력 분포를 강제로 일치시킵니다.

### B. 연속 번역을 위한 비제어(Continuous) 슬라이딩 윈도우
기존의 수어 번역 시도는 사용자가 시작 버튼을 누르고 특정 시간 동작을 취한 뒤 멈추는 동적 제어가 필요했으나, SignLingo는 스트라이드 슬라이딩 구조를 채택하여 실시간 카메라 수신 데이터를 밀어내며 초당 수 차례 이상 백그라운드 추론을 유기적으로 이어가는 진정한 의미의 **실시간 연속 번역**을 달성했습니다.

### C. 메모리 및 CPU 성능 극대화
* **NumPy Memory Map (`np.memmap`):** 백엔드에서 5GB 이상의 대용량 바이너리 파일을 RAM 메모리에 통째로 로딩하면 로컬 컴퓨터 자원이 급격히 소모됩니다. 이를 위해 memmap 가상 메모리 매핑 기법을 적용하여 파일 포인터 수준에서 온디맨드로 필요한 데이터 슬라이스만 읽어 전송합니다.
* **사전 할당 텐서 버퍼:** FastAPI 추론 요청 시마다 신규 PyTorch 텐서를 GPU에 동적 할당하면 극심한 오버헤드가 발생합니다. 백엔드 시동 시 고정 크기(`[1, 60, 100]`)의 텐서 버퍼를 GPU 영역에 미리 할당해두고 incoming 데이터를 복사(`_input_buffer.copy_`)하여 지연 시간을 획기적으로 줄였습니다.

## 4. 아키텍처 개선 제안 (Architectural Recommendations)

1. **상태 관리 도구로 Zustand 도입 (Zustand State Offloading)**
   * 현재 `LessonRoom.jsx`는 `videoRef`, `canvasRef`, `poseDataRef` 등 다수의 리액트 Ref와 State가 혼재되어 잦은 상태 변동 시 컴포넌트 갱신 성능 부하를 가집니다.
   * 프레임별 리타겟팅 좌표 데이터 및 실시간 AI 번역 단어 로그 등은 리액트 리렌더링과 물리적으로 격리된 Zustand 전역 저장소로 이전하는 것을 권장합니다.

2. **Web Worker를 활용한 MediaPipe 추론 스레드 분리**
   * 현재 MediaPipe의 `detectForVideo` 메서드가 메인 JS 스레드 상에서 30fps 속도로 프레임 분석을 직접 수행하고 있습니다. 저사양 노트북이나 모바일 등에서는 메인 UI 스레드가 블로킹되어 프레임 드랍이 발생할 수 있습니다.
   * `FilesetResolver` 및 `PoseLandmarker`/`HandLandmarker`를 전용 **Web Worker** 파일로 패키징하고 오프스크린 캔버스 기술을 도입하여 백그라운드 스레드에서 Landmarks를 추출하게 만들면 부드러운 60fps 화면 재생을 보장할 수 있습니다.

3. **Gemini API 문장 재생성 파이프라인의 프론트엔드 연동**
   * 백엔드에는 구현되어 있으나 프론트엔드 단에서 아직 활성화되지 않은 `/api/generate-sentence` API를 연속 번역기 페이지(`Translator.jsx`)에 연결해야 합니다.
   * 수어로 순차 번역된 파편화된 단어 배열들을 사용자가 "번역 완료" 혹은 실시간 대기 3초 이상 경과 시 백엔드 Gemini 2.5 Flash를 거쳐 자연스러운 구어체 문장으로 다듬어 화면에 표출하는 UX 보완이 시급합니다.
